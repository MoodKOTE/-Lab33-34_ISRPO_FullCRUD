## Описание проекта

**NotesApp** — это backend-приложение на ASP.NET Core, реализующее полноценный CRUD для управления заметками с категориями.  
Проект демонстрирует:

- Связь «один-ко-многим» между таблицами **Category** (категория) и **Note** (заметка).
- Паттерн **Repository** для отделения логики доступа к данным от контроллеров.
- Валидацию через **Data Annotations** и единый формат ответов `ApiResponse<T>`.
- Фильтрацию, поиск, сортировку и пагинацию заметок.
- Автоматическое применение миграций при запуске.

Приложение позволяет создавать категории (например, «Работа», «Учёба», «Личное») и добавлять заметки с заголовком, содержимым, приоритетом, а также закреплять или архивировать их.

## Маршруты API

Все ответы обёрнуты в единый формат `ApiResponse<T>` и содержат поля `success`, `data`, `message`, `statusCode`.



##  Паттерн Repository

**Repository** — это структурный паттерн проектирования, который изолирует логику доступа к данным от бизнес-логики контроллеров.

### Зачем он нужен?

| Проблема без Repository | Решение с Repository |
|------------------------|----------------------|
| Логика запросов к БД размазана по контроллерам | Все запросы собраны в одном месте |
| Трудно тестировать контроллер без реальной БД | Можно подменить репозиторий на тестовый (mock) |
| При смене БД нужно менять все контроллеры | Меняется только реализация репозитория |
| Дублирование одинаковых запросов | Переиспользуемые методы (например, `ExistsAsync`) |


## Главные выводы
1. Паттерн Repository — не лишняя абстракция, а способ держать код управляемым при росте проекта
2. Data Annotations решают двойную задачу: валидируют входные данные и задают ограничения в БД.
3. Единый формат ответа (ApiResponse) упрощает жизнь фронтенду — он всегда знает, что ждать от сервера
4. DeleteBehavior.Restrict защищает данные от случайного каскадного удаления
5. Include() и проекция в DTO через Select() — правильный способ получить связанные данные без N+1 проблемы
